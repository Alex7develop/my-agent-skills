# Safe Refactoring

Ключевое отличие рефакторинга от любой другой правки: внешнее поведение
не меняется. Если в процессе хочется "а заодно исправить вот эту логику" —
это уже не рефакторинг, и это стоит выделить в отдельный шаг.

## Предусловие

Перед началом рефакторинга должны быть тесты, покрывающие текущее
поведение. Если тестов нет — сначала написать характеризующие тесты
("characterization tests"), которые фиксируют текущее поведение как есть
(даже если оно неидеальное), и только потом начинать менять структуру.

## Процесс

1. **Зафиксировать текущее поведение тестами** (см. предусловие).
2. **Работать тонкими шагами.** Один рефакторинг за раз (переименование,
   выделение функции, перемещение кода) — не смешивать несколько видов
   изменений в одном шаге.
3. **Прогонять тесты после каждого шага.** Если тесты не написаны заново —
   значит, шаг не должен был менять поведение, и любой красный тест — сигнал
   немедленно откатиться, а не чинить дальше.
4. **Коммитить после каждого зелёного шага.** Маленькие коммиты — это
   возможность откатиться на последний работающий шаг, а не переписывать всё
   с нуля при ошибке.
5. **Отделять структурные изменения от изменений поведения.** Если во время
   рефакторинга видна реальная фича/фикс — зафиксировать это отдельно и не
   смешивать с текущим PR.

## Частые виды безопасного рефакторинга

- Выделение функции/метода из длинного блока кода
- Переименование для ясности (переменные, функции, файлы)
- Устранение дублирования через общую абстракцию
- Замена условной логики на полиморфизм/таблицу диспетчеризации
- Разбиение большого модуля на несколько с чёткими границами

## Чек-лист перед тем, как считать рефакторинг завершённым

- [ ] Все существующие тесты зелёные без изменений в самих тестах
- [ ] Внешний API/контракт модуля не изменился (если изменился — это не
      чистый рефакторинг, нужно явно об этом сказать)
- [ ] Каждый шаг был закоммичен отдельно, коммиты можно откатить по одному
- [ ] Нет смешанных изменений "рефакторинг + фича" в одном шаге
