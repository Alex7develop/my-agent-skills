# Spec First

Модели по умолчанию сразу начинают писать код. Это создаёт риск: агент решит
задачу, которую пользователь не совсем имел в виду. Эта короткая спека —
дешёвый способ синхронизироваться до того, как написана хоть одна строка.

## Когда использовать

- Новая фича или новый модуль
- Заметное изменение существующего поведения
- Задача, которую можно интерпретировать 2+ способами

## Когда пропустить

- Однострочные правки, опечатки, явно узкие багфиксы
- Пользователь уже дал детальную спецификацию сам

## Процесс

1. **Уточнить цель.** Сформулировать одним предложением, что должно
   получиться, и явно проверить это с пользователем, если формулировка задачи
   допускает разночтения.
2. **Обозначить границы (scope).** Что входит в задачу и что явно НЕ входит.
   Незакрытые границы — самая частая причина переделок.
3. **Зафиксировать интерфейс/контракт.** Входы, выходы, побочные эффекты,
   формат ошибок — до реализации, не после.
4. **Критерии готовности.** 3-5 проверяемых пунктов ("работает, если...").
   Это станет основой тест-кейсов на следующем шаге (TDD).
5. **Явно перечислить риски и допущения.** Если что-то неочевидно —
   зафиксировать предположение и продолжить, а не блокироваться на вопросах.

## Формат вывода

Короткий блок из 4 секций перед началом реализации:

```
## Spec: <название>
**Цель:** ...
**В скоуп / вне скоупа:** ...
**Контракт:** входы / выходы / ошибки
**Готово, когда:** - [ ] ... - [ ] ... - [ ] ...
```

Не превращай это в бюрократию — спека должна занимать 5-10 строк, не страницу.
Цель — синхронизация, а не документооборот.
