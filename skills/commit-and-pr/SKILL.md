# Commit & PR

Коммит и PR — это не формальность, а способ передать контекст будущему
читателю (включая вас самих через месяц). Сообщение должно объяснять
"почему", а не только "что" — "что" видно из diff'а.

## Атомарность коммитов

Один коммит — одно логическое изменение. Разделять на отдельные коммиты:
- Структурные изменения (переименования, перемещения) отдельно от
  изменений логики
- Рефакторинг отдельно от фич/фиксов
- Обновление зависимостей отдельно от изменений кода

Если сложно описать коммит одним предложением без "и" — вероятно, он
делает больше одной вещи и стоит разбить.

## Формат сообщения коммита

```
<тип>: короткое summary в повелительном наклонении (≤50 символов)

Более подробное объяснение, если нужно: что изменилось и, главное,
ПОЧЕМУ — какую проблему решает изменение, какие альтернативы
рассматривались и почему выбран этот подход.

Refs: #123 (если применимо)
```

Типы (conventional commits, опционально, если в проекте принят такой
стиль): `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`.

## Описание Pull Request

```
## Что и почему
Краткое описание изменения и мотивации (ссылка на issue/спеку, если есть).

## Как проверить
Конкретные шаги для ревьюера: команды, сценарии, что должно получиться.

## Риски / что не покрыто
Честно указать ограничения, побочные эффекты, что осталось за скоупом.
```

## Чек-лист перед тем, как оформить PR

- [ ] Каждый коммит в PR можно откатить по отдельности без поломки сборки
- [ ] Сообщения коммитов объясняют "почему", не только "что"
- [ ] Описание PR даёт ревьюеру достаточно контекста без чтения всего diff'а
- [ ] Указаны риски/ограничения, если они есть — не скрыты и не замолчаны
