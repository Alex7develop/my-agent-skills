# Code Review

Пять осей проверки. Не пытаться "найти хоть что-то" на каждой оси —
если ось не даёт находок, честно писать "нет замечаний", это лучше, чем
притянутые мелочи.

## Пять осей

1. **Корректность.** Делает ли код то, что задумано? Обработаны ли
   граничные случаи (пустой вход, null, переполнение, конкурентный доступ)?
2. **Читаемость.** Поймёт ли код человек, не писавший его, без объяснений?
   Имена, структура, отсутствие "магии".
3. **Безопасность.** Валидация входных данных, инъекции, секреты в коде,
   права доступа, обработка пользовательского ввода.
4. **Производительность.** Есть ли очевидные проблемы (N+1 запросы,
   O(n²) там где легко сделать O(n log n), утечки памяти/хендлов)? Не
   заниматься микрооптимизацией там, где это не нужно.
5. **Тесты.** Покрыты ли изменения тестами? Тестируют ли они поведение,
   а не только "счастливый путь"?

## Процесс

1. Понять контекст изменения (что и зачем меняется) прежде чем оценивать —
   спека или описание PR, если есть.
2. Пройти по каждой из пяти осей отдельно, не смешивая находки.
3. Разделить находки по серьёзности:
   - **Блокирует мерж** — баги, дырки безопасности, потеря данных
   - **Стоит исправить** — читаемость, дублирование, слабое покрытие тестами
   - **Опционально / на вкус** — стилистические предложения
4. Для каждой находки — конкретное место (файл/строка) и конкретное
   предложение, а не общая формулировка вроде "можно лучше".

## Формат вывода

```
## Code Review

### Блокирует мерж
- [файл:строка] ...

### Стоит исправить
- [файл:строка] ...

### Опционально
- ...

### Без замечаний
- <оси, где всё в порядке>
```

## Анти-паттерны, которых нужно избегать

- Не придумывать проблемы там, где их нет, только чтобы "было что сказать"
- Не давать общие советы без привязки к конкретному коду
- Не путать личные стилистические предпочтения с объективными проблемами —
  явно помечать субъективные замечания как "на вкус"
